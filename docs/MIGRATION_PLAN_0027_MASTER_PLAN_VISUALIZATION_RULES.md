# خطة ترحيل 0027 — قواعد عرض KPI لـ Master Plan

## الهدف والنطاق

تضيف الدفعة جدول `master_plan_visualization_rules` لحفظ قواعد تلوين وعتبات العرض الخاصة بمشروع واحد. يعالج ذلك عتبات التقدم وألوان الحالة وانحراف التكلفة في الخريطة المكانية، من دون تحويل ألوان الواجهة إلى حقيقة تجارية أو إتاحة قاعدة من مشروع آخر.

| القرار | التطبيق |
|---|---|
| نطاق السجل | `tenantId` و`projectId` إلزاميان؛ القاعدة تخص المشروع ولا تورث عبر المستأجرين. |
| مفتاح العمل | صف واحد لكل `metric` ضمن المشروع بواسطة قيد فريد `tenantId, projectId, metric`. |
| البيانات المرنة | يخزن `rulesJson` القواعد المقيدة من عقد tRPC فقط، ولا يقبل JSON خامًا من واجهة العميل. |
| القراءة | تتطلب `PROJECT/project.read` وميزة `MASTER_PLAN` وملكية المشروع. |
| الكتابة | تتطلب `PROJECT/project.write` والميزة ذاتها؛ تحفظ القاعدة وسجل التدقيق في معاملة واحدة. |
| الأثر | إضافة جدول وفهارس ومفاتيح خارجية فقط؛ لا تعديل أو حذف لجداول أو بيانات قائمة. |

## التحقق قبل التطبيق

ينشئ `pnpm drizzle-kit generate` ترحيلًا جديدًا فقط. تراجع SQL للتأكد من وجود جدول وفهرس وقيد فريد ومراجع `companies` و`projects` و`users`، ومن عدم وجود `DROP` أو `ALTER` مدمر. تقصر أسماء المفاتيح الأجنبية عند الحاجة لتوافق حد معرّفات TiDB/MySQL.

## التحقق بعد التطبيق

يُتحقق من `information_schema.tables` و`information_schema.statistics` و`information_schema.key_column_usage` لوجود الجدول وقيد الفهرس والمراجع. يثبت تكامل MySQL/TiDB رفض القراءة أو التحديث عبر مشروع عابر، ثم حفظ قاعدة مرخصة واستعادتها والتحقق من تدقيق `master_plans.visualization_rule_saved`.

## الاسترجاع

إن تعذر نشر التطبيق بعد الترحيل، يوقف استخدام العقود الجديدة ويستعاد إلى نقطة تحقق التطبيق السابقة. لا ينفذ إسقاط الجدول تلقائيًا؛ أي تراجع بنيوي لاحق يتطلب مراجعة مستقلة لتأثير القواعد التي قد ينشئها المستخدمون.
