# ADR-0001: حماية سجل التدقيق عبر حسابات قاعدة البيانات

**الحالة:** ~~معتمد للتنفيذ قبل Pilot~~ — **حلّ محله `ADR-0002-POSTGRES-SUPABASE-VERCEL.md`** (22 أكتوبر 2026): المحرك صار PostgreSQL وحماية `audit_logs` صارت triggers + REVOKE. يبقى هذا الملف سجلًا تاريخيًا لقرار TiDB.  
**التاريخ:** 20 أغسطس 2026.  
**النطاق:** PROJECT OS فقط على MySQL/TiDB Serverless.

## السياق

تكتب خدمات PROJECT OS أحداث `audit_logs` داخل معاملة العمل نفسها، لكن TiDB Serverless لا يوفر مشغلات قاعدة البيانات المطلوبة لمنع `UPDATE` و`DELETE` على هذا الجدول. لذلك لا يصح وصف السجل الحالي بأنه غير قابل للتلاعب على مستوى قاعدة البيانات، حتى لو كانت جميع مسارات التطبيق لا تقدم عملية تحديث أو حذف له.

## القرار

يبقى PROJECT OS على **MySQL/TiDB Serverless** و`drizzle-orm/mysql2` في مرحلة الـPilot. ينفذ مسؤول قاعدة البيانات فصل الحسابات الآتي، وتكون نتيجة `SHOW GRANTS` والتحقق السلبي جزءًا من دليل قبول الـPilot.

| الحساب | الاستخدام | امتيازات `audit_logs` المسموح بها | محظور صراحة |
|---|---|---|---|
| `project_os_app` | تشغيل Express/tRPC اليومي | `SELECT`, `INSERT` | `UPDATE`, `DELETE`, `ALTER`, `DROP`, `GRANT` |
| `project_os_schema_admin` | الترحيلات والاستعادة والتشخيص المصرح به فقط | حسب سياسة منصة البيانات وحساب مسؤول منفصل | لا يستخدم في خدمة التطبيق أو في بيئة التشغيل اليومية |
| `project_os_audit_reader` | القراءة والمراجعة والتصدير المتحكم به عند الحاجة | `SELECT` | كل الكتابات وتغيير المخطط والمنح |

> لا يمثل حظر `UPDATE` و`DELETE` على حساب التطبيق مشغل قاعدة بيانات ولا يمنع حسابًا إداريًا ذا امتيازات أعلى. هو ضابط وصول تشغيلي صريح يقلل مسار التلاعب المعتاد، ويجب عرضه بهذه الصياغة أمام عميل الـPilot وأي جهة تدقيق.

## حدود الضابط: حيازة اعتماد التدقيق الإداري

الفصل الحالي قائم على **مستوى المنح**، لا على مستوى **حيازة الاعتماد**. في بيئة مشروع Manus الحالية، يقع اعتماد حساب التطبيق المقيد واعتماد حساب التدقيق الإداري في ملف تهيئة محلي واحد للبيئة. لذلك لا يجوز وصف الفصل بين الحسابين بأنه فصل تشغيلي كامل داخل تلك البيئة: أي عملية أو طرف يملك وصولًا إلى الملف والبيئة قد يستخدم اعتماد الحساب الإداري لتجاوز قيد حساب التطبيق.

لا يعني ذلك وقوع انكشاف خارجي أو وجود سر في Git؛ فملف التهيئة غير متتبع ولم يظهر في تاريخ Git أو `github/main` عند فحص 21 أغسطس 2026. لكنه حد معماري وتشغيلي قائم يجب الإفصاح عنه صراحةً.

**شرط الإغلاق قبل بيانات عميل حقيقية:** يدور مالك البيانات كلمتي المرور، ثم يخرج `PROJECT_OS_AUDIT_ADMIN_PASSWORD` نهائيًا من بيئة البناء والوكيل وملف التهيئة المحلي. يحتفظ المالك أو مسؤول قاعدة البيانات المخول بالاعتماد الإداري خارج بيئة التطبيق ويستخدمه من كونسول قاعدة البيانات عند الاستثناء المصرح به فقط. لا يكفي تغيير الاسم أو فصل المتغيرات داخل الكود.

## Runbook التنفيذ الخارجي

ينفذ **مسؤول قاعدة البيانات المخول فقط** الخطوات على بيئة الـPilot بعد تكييف أسماء المستخدمين والمضيف والمنصة. لا تشغل هذه الأوامر من خدمة التطبيق أو من قاعدة التكامل.

```sql
-- مثال سياسة، وليس أمرًا ذاتي التنفيذ داخل PROJECT OS.
-- أنشئ الحسابات وفق آلية TiDB Cloud/مزود الهوية المعتمد.

GRANT SELECT, INSERT ON project_os.audit_logs TO 'project_os_app'@'%';
REVOKE UPDATE, DELETE ON project_os.audit_logs FROM 'project_os_app'@'%';

GRANT SELECT ON project_os.audit_logs TO 'project_os_audit_reader'@'%';

-- تحدد امتيازات بقية الجداول للتطبيق وفق أقل صلاحية لازمة،
-- ولا يُمنح الحساب التشغيلي CREATE USER أو GRANT أو ALTER أو DROP.
SHOW GRANTS FOR 'project_os_app'@'%';
SHOW GRANTS FOR 'project_os_audit_reader'@'%';
```

ينفذ المسؤول بعدها اختبارًا بحساب `project_os_app`: إنشاء حدث تدقيق مسموح، ثم محاولة `UPDATE audit_logs` ومحاولة `DELETE FROM audit_logs`، ويحتفظ برسالة الرفض أو رمز الخطأ. يراجع كذلك أن اتصال التطبيق يستخدم الحساب التشغيلي لا حساب الترحيل أو المسؤول، ثم يسجل تاريخ المراجعة والمسؤول والبيئة في سجل تشغيل الـPilot.

## معايير قبول الـPilot

| الشرط | الدليل المطلوب | الحالة الآن |
|---|---|---|
| حساب تطبيق منفصل | اسم الحساب غير السري ومصدر اتصال التشغيل | معلق على مسؤول قاعدة البيانات |
| عدم وجود تعديل أو حذف للسجل لحساب التطبيق | `SHOW GRANTS` واختبارا رفض موثقان | معلق على مسؤول قاعدة البيانات |
| فصل حساب الترحيلات | إثبات أن خدمة التطبيق لا تستخدم حساب المسؤول | معلق على مسؤول قاعدة البيانات |
| فصل حيازة اعتماد التدقيق الإداري | إثبات تدوير كلمتي المرور وغياب `PROJECT_OS_AUDIT_ADMIN_PASSWORD` عن بيئة البناء والوكيل، مع حيازة المالك/مسؤول القاعدة له خارجها | معلق على مالك البيانات ومسؤول قاعدة البيانات؛ مانع قبل بيانات عميل حقيقية |
| إفصاح للعميل | مراجعة قانونية/تجارية لصياغة الضمان الفعلي | معلق على مالك المنتج والشؤون القانونية |
| عدم ادعاء حصانة trigger | نسخ الـPilot والتوثيق يذكران الضابط وحدوده | منفذ في وثائق PROJECT OS |

## تبعات القرار

تستمر كل ترحيلات واختبارات ونشرات PROJECT OS على MySQL/TiDB Serverless. يبقى الحارس الخادمي والعزل والتدقيق الذري كما هما؛ يضيف هذا القرار طبقة دفاع وصول قابلة للتحقق، لكنه لا يتحول إلى ادعاء بعدم قابلية التلاعب ما لم تنفذ أدلة القبول أعلاه.
