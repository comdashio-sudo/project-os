## 2. المقترح: تراجع محدود لعمليتين

| السؤال | المقترح |
|---|---|
| **العمليات المدعومة** | (1) دفعة «تحديث الإنجاز»، (2) دفعة «استلام QC». لا غيرهما في المرحلة الأولى |
| **الوحدة** | الدفعة كلها (كل فلل الحفظ الواحد)، لا خلية واحدة |
| **مدة السماح** | 15 دقيقة من الحفظ، بساعة الخادم |
| **من يحق له** | صاحب الحفظ نفسه وحده، بالصلاحية التي حفظ بها (`project.progress.manage` أو `project.qc.receive`) على المشروع نفسه. مدير المشروع لا يتراجع عن حفظ غيره (يصحّح بحفظ جديد) |
| **الطريقة** | **لا حذف أبدًا:** التراجع حفظ جديد يعيد كل خلية إلى حالتها قبل الدفعة (`fromStatus`)، فيُكتب صف تاريخ جديد لكل خلية (من الحالي إلى السابق) بملاحظة `undo <batchId>` |
| **سجل التدقيق** | صف `pmc.progress_batch_undone` / `pmc.qc_receipt_batch_undone` يحمل الدفعة الأصلية وعدد الخلايا؛ والسجل الأصلي يبقى كما هو (append-only) |
| **إن عدّل غيره بعده** | إن تغيّرت أي خلية في الدفعة بعد الحفظ (حفظ آخر، أو اعتماد تقرير يومي حرّكها، أو QC عليها) **يُرفض التراجع كله** ويسمّي الفلل المتغيّرة؛ لا تراجع جزئي |
| **مرة واحدة** | الدفعة تُتراجع مرة واحدة؛ ولا «تراجع عن التراجع» (يُحفظ من جديد) |
| **الممنوع** | العمليات المالية المعتمدة (التكاليف المرحّلة، الفواتير، المستخلصات، الرواتب)، وحركات المستودع (لها الإرجاع والتسوية)، والتقرير اليومي بعد إرساله، والاستيراد (له التراجع الخاص به)، وأي خلية مكتملة دخلت مستخلصًا أو قيمة مكتسبة معتمدة |

## 3. ما يحتاجه التنفيذ بعد الموافقة

- **الإنجاز:** لا ترحيلة — الدفعة معروفة من `batchId` في التدقيق وملاحظة صفوف التاريخ. إجراء خادم `pmc.undoProgressBatch` بالحدود أعلاه.
- **QC:** ترحيلة صغيرة تضيف `batch_id` (يقبل الفراغ) إلى `pmc_qc_receipt_events` ويكتبه الحفظ؛ الدفعات القديمة بلا معرّف لا تُتراجع.
- **الواجهة:** بعد الحفظ رسالة «حُفظ — تراجع» لمدة السماح، تختفي بعدها.
- **الاختبارات:** موجب (التراجع يعيد الحالات ويكتب التاريخ والتدقيق)، وسالب لكل حد (بعد 15 دقيقة، شخص آخر، خلية تغيّرت بعده، تراجع ثانٍ، مشروع/شركة أخرى، بلا صلاحية).
