## قواعد إلزامية

| المبدأ | التطبيق في PROJECT OS |
|---|---|
| الدليل لا الادعاء | لا يُعلن نجاح أي ميزة بناءً على البناء فقط؛ يوثق الاختبار ومدخلاته ونتيجته وحدوده. |
| الحالة الخاطئة مستحيلة | تفرض قواعد البيانات القيود والمفاتيح والعلاقات، ويفرض الخادم الصلاحيات؛ الواجهة لا تعد طبقة فرض. |
| عزل المستأجرين | يحمل كل سجل تشغيلي مفتاح المستأجر؛ يُثبت الوصول بنطاق المستأجر والمشروع، ويُختبر ضد سجلات مستأجر آخر. |
| صلاحيات الكتالوج | لا تُشفّر الأدوار في مسارات الأعمال؛ تعود الصلاحية إلى كتالوج الصلاحيات والعلاقات. |
| تاريخ غير قابل للتزوير | يسجل التدقيق من الخادم فقط؛ لا يقبل العميل من يملك السجل أو هوية منفذه. |
| الدفعات المنضبطة | قبل أي تغيير قاعدة بيانات: كتابة مخططة، أثر متوقع، استعلام تحقق، ومسار استرجاع. |
| المسارات الشقيقة | عند إصلاح إدخال أو تحديث، تُفحص المسارات الشقيقة قبل إعلان المعالجة. |
| ثنائية اللغة | كل نص ظاهر للمستخدم، بما فيه حالات الخطأ والفراغ، يجب أن يتوفر بالعربية والإنجليزية؛ العربية RTL أصلًا. |

## أنماط الفشل التي نفحصها

- الفشل الصامت: لا تعتبر الكتابة ناجحة إلا بدليل عائد قابل للتحقق.
- اليتيم: تعدّد المسارات إلى الحالة يقتضي حراسة نقطة التقارب، لا واجهة منفردة.
- الإغلاق الضيق: نختبر المسارات الشرعية بعد كل قيد أو تضييق صلاحية.
- الفخ: نعيد فحص الإخفاقات الصامتة بعد التغييرات التي تضيف تبعيات جديدة.
- النسبة الكاذبة: نعرض عدادًا مع مقام محدد، لا نسبة بلا تعريف.
- الرقم الواثق الخاطئ: لا ننسب الفشل إلى تغيير جديد إلا بعد إعادة الإنتاج.
- المسار الشقيق: نفحص الإدخال والتحديث والمسارات المتجاورة عند العثور على خلل.
