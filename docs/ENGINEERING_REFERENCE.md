# مرجع الهندسة الدائم

المصدر المعتمد: `Pasted_content_03.txt` الذي قدّمه المستخدم. يجب قراءة المرجع كاملًا قبل أي دفعة تطويرية مهمة، وتطبيقه كمعيار تشغيل لا كقائمة ميزات.

## قواعد إلزامية

| المبدأ | التطبيق في PROJECT OS |
|---|---|
| الدليل لا الادعاء | لا يُعلن نجاح أي ميزة بناءً على البناء فقط؛ يوثق الاختبار ومدخلاته ونتيجته وحدوده. |
| الحالة الخاطئة مستحيلة | تفرض قواعد البيانات القيود والمفاتيح والعلاقات، ويفرض الخادم الصلاحيات؛ الواجهة لا تعد طبقة فرض. |
| عزل المستأجرين | يحمل كل سجل تشغيلي مفتاح المستأجر؛ يُثبت الوصول بنطاق المستأجر والمشروع، ويُختبر ضد سجلات مستأجر آخر. |
| صلاحيات الكتالوج | لا تُشفّر الأدوار في مسارات الأعمال؛ تعود الصلاحية إلى كتالوج الصلاحيات والعلاقات. |
| تاريخ غير قابل للتزوير | يسجل التدقيق من الخادم فقط؛ لا يقبل العميل من يملك السجل أو هوية منفذه. |
| الدفعات المنضبطة | قبل أي تغيير قاعدة بيانات: كتابة مخططة، أثر متوقع، استعلام تحقق، ومسار استرجاع. |
| المسارات الشقيقة | عند إصلاح إدخال أو تحديث، تُفحص المسارات الشقيقة قبل إعلان المعالجة. |
| ثنائية اللغة | كل نص ظاهر للمستخدم، بما فيه حالات الخطأ والفراغ، يجب أن يتوفر بالعربية والإنجليزية؛ العربية RTL أصلًا. |

## أنماط الفشل التي نفحصها

- الفشل الصامت: لا تعتبر الكتابة ناجحة إلا بدليل عائد قابل للتحقق.
- اليتيم: تعدّد المسارات إلى الحالة يقتضي حراسة نقطة التقارب، لا واجهة منفردة.
- الإغلاق الضيق: نختبر المسارات الشرعية بعد كل قيد أو تضييق صلاحية.
- الفخ: نعيد فحص الإخفاقات الصامتة بعد التغييرات التي تضيف تبعيات جديدة.
- النسبة الكاذبة: نعرض عدادًا مع مقام محدد، لا نسبة بلا تعريف.
- الرقم الواثق الخاطئ: لا ننسب الفشل إلى تغيير جديد إلا بعد إعادة الإنتاج.
- المسار الشقيق: نفحص الإدخال والتحديث والمسارات المتجاورة عند العثور على خلل.

## شرط التقرير

يعرض كل تقرير: ما جُرّب، المخرجات الخام ذات الصلة، ما تغيّر، ما بقي مفتوحًا، وما لم يمكن التحقق منه ولماذا.

## مصفوفة فرض النواة الحالية

| القاعدة | التصنيف الحالي | الدليل المتاح | فجوة يجب إغلاقها |
|---|---|---|---|
| عزل المستأجر | الخادم + قاعدة البيانات | `tenantId` على جداول الأعمال، وفحوصات التفويض في خدمات المستأجر والمشروع. | اختبارات تكامل مباشرة لسجل مستأجر آخر مطلوبة. |
| حد حزمة المنتج | الخادم | `assertTenantAccess` قبل إجراءات المشروع وEVM. | يجب إضافة اختبار API لكل إجراء تشغيلي، لا قراءة المصدر فقط. |
| نطاق المشروع | الخادم + تكامل قاعدة البيانات | يتحقق `assertWbsItemWithinProject` من المستأجر والمشروع قبل كتابة الميزانية والتكلفة والتقدم. ويثبت تكامل MySQL/TiDB رفض WBS من مشروع شقيق داخل المستأجر قبل كل كتابة، ثم السماح لـWBS المملوك. | يجب تطبيق الدليل نفسه على أي مسار جديد يقبل معرّف WBS أو تكلفة أو تقدم. |
| EVM | خدمة مجال + تكامل قاعدة البيانات | اختبارات الوحدة تغطي المعادلات والحواف، ويثبت تكامل MySQL/TiDB لقطة تشغيلية من نشاط وتقدم وتكلفة وميزانية فعلية بقيم PV/EV/AC/BAC متوقعة وسجل تدقيق. | يجب إضافة دليل التكامل نفسه عند توسيع مصادر EVM أو أساليب الحساب. |
| سجل التدقيق | الخادم، مع فجوة بيئية موثقة | تكتب الإجراءات الأساسية سجلات تدقيق من الخادم، والمسارات التشغيلية الجديدة تكتبها ذريًا مع السجل التشغيلي. | لا يمكن إنشاء مشغلات منع `UPDATE`/`DELETE` في TiDB Serverless لأن TiDB لا يدعم المشغلات؛ يلزم حساب تشغيل محدود أو MySQL/InnoDB لإغلاق الفجوة على مستوى قاعدة البيانات. |
| تبديل اللغة | العميل + وثيقة DOM | `LanguageContext` يضبط `lang` و`dir` ويحفظ الاختيار؛ تحقق بصري عربي/إنجليزي. | رسائل الخادم الخام ما زالت تحتاج خريطة أخطاء ثنائية اللغة. |

### نتيجة تدقيق أولي لمسارات الكتابة

تمت مراجعة إجراءات إنشاء المشروع، ولقطة EVM، وWBS، والتكلفة، والتقدم، والميزانية. جميعها تمر عبر `assertTenantAccess` قبل الكتابة. تتحقق إجراءات المشروع ولقطة EVM وWBS من أن المشروع تابع للمستأجر، وتستدعي مسارات التكلفة والتقدم والميزانية `assertWbsItemWithinProject` عند ورود `wbsItemId`. يثبت تكامل MySQL/TiDB الآن رفض WBS من مشروع شقيق في المستأجر نفسه قبل إنشاء ميزانية أو تكلفة أو تقدم، مع إثبات السماح للـWBS المملوك.
