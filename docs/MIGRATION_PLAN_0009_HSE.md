# خطة ترحيل 0009 — سجل ملاحظات HSE

## الغرض

إضافة سجل ملاحظات الصحة والسلامة والبيئة (**HSE**) المرتبط بمشروع واحد داخل مستأجر واحد. لا يتلقى الجدول مستخدمًا أو مستأجرًا من الواجهة دون أن يفرض الخادم نطاقهما عند الكتابة.

## التغيير المخطط

ينشئ الترحيل جدول `hse_observations` بالحقول التالية: معرف، مستأجر، مشروع، رقم ملاحظة فريد داخل المشروع، عنوان، وصف، تصنيف (`safety` أو `health` أو `environment`)، شدة (`low` أو `medium` أو `high` أو `critical`)، حالة، تاريخ استحقاق اختياري، ومنشئ السجل وتواريخ الخادم. تعتمد دورة الحالة على الانتقالات الخادمية `open → assigned → remediation → verification → closed`، مع السماح بالإلغاء من الحالات المفتوحة فقط.

## قيود الأثر

| القيد | آلية الفرض |
|---|---|
| عزل المستأجر | `tenantId` غير فارغ ومفتاح أجنبي إلى `companies`، مع فهرس يبدأ بالمستأجر. |
| عزل المشروع | `projectId` غير فارغ ومفتاح أجنبي إلى `projects`، وتفرض الخدمة المطابقة للمستأجر. |
| منع تكرار رقم السجل | مفتاح فريد على `(projectId, observationNumber)`. |
| قراءة السجل | حزمة PROJECT وصلاحية `project.read` ونطاق المشروع في الخادم. |
| كتابة وانتقال السجل | حزمة PROJECT وصلاحية `project.write` ونطاق المشروع وتدقيق ذري في الخادم. |
| التاريخ | لا توجد هوية منشئ أو زمن تدقيق قابلان للإرسال من العميل. |

## SQL المتوقع

ينشئ `drizzle/0009_hse_observations.sql` جدولًا مستقلًا وفهارس القراءة المقيدة، دون تعديل أو حذف بيانات قائمة. لا يستخدم مشغلات، لأن TiDB Serverless لا يدعمها؛ وهذه ليست آلية لتعويض الفجوة الموثقة لحماية `audit_logs`.

## التحقق بعد التطبيق

يُنفذ استعلام كتالوج للتحقق من وجود `hse_observations` وفهرس `hse_observations_tenant_project_status_due_idx`، ثم يثبت اختبار API إنشاء سجل مرخّص مع تدقيق ذري، ورفض قراءة أو انتقال سجل خارج المستأجر أو المشروع.

## الاسترجاع

إذا فشل التطبيق قبل أي بيانات تشغيلية، يكون الاسترجاع `DROP TABLE hse_observations`. بعد وجود بيانات تشغيلية لا ينفذ الاسترجاع الحذفي تلقائيًا؛ يلزم تصدير ومراجعة موافقة تشغيلية قبل أي حذف.
