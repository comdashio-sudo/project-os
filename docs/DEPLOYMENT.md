# دليل نشر وتشغيل PROJECT OS

## نطاق الدليل

يصف هذا الدليل النشر الفعلي لمنصة **PROJECT OS**. تعتمد المنصة على React وTypeScript وExpress وtRPC وDrizzle ORM وقاعدة **MySQL/TiDB Serverless** عبر `drizzle-orm/mysql2`. لا تستخدم المنصة Supabase أو PostgreSQL في بيئة التشغيل الحالية.

> لا تعدّ عملية البناء وحدها دليل نشر. يتطلب الإغلاق نجاح اختبارات الوحدة والأنواع والبناء، ثم اختبار قاعدة التكامل المعزولة عند توفر اتصالها.

## متطلبات البيئة

| المتغير | الاستخدام | مصدره |
|---|---|---|
| `DATABASE_URL` | اتصال التشغيل إلى MySQL/TiDB. | إدارة البيئة الآمنة فقط. |
| `TEST_DATABASE_URL` | اتصال قاعدة `project_os_integration_test` المعزولة. لا يوجه إلى قاعدة التشغيل. | إدارة البيئة الآمنة فقط. |
| `JWT_SECRET` | توقيع جلسة المصادقة. | مزود بيئة التشغيل. |
| `OAUTH_SERVER_URL` و`VITE_APP_ID` و`VITE_OAUTH_PORTAL_URL` | مصادقة Manus OAuth. | مزود بيئة التشغيل. |
| `BUILT_IN_FORGE_API_URL` و`BUILT_IN_FORGE_API_KEY` | خدمات التخزين المدمجة على الخادم. | مزود بيئة التشغيل. |

لا تُسجل القيم الفعلية لهذه المتغيرات في المستودع أو ملفات التوثيق. وإذا احتاج متغير جديد، يضاف عبر إدارة الأسرار لا عبر ملف `.env` ملتزم.

## مسار النشر

يبدأ النشر بمراجعة مخطط `drizzle/schema.ts`. عند تغيير مخطط MySQL/TiDB، ينفذ الفريق التسلسل الآتي:

```bash
cd /home/ubuntu/project-os
pnpm drizzle-kit generate
# راجع ملف SQL المولد ضمن drizzle/ قبل التطبيق
pnpm test && pnpm check && pnpm build
```

بعد مراجعة SQL بحثًا عن عمليات مدمرة أو غير متوقعة، يطبق الترحيل على قاعدة التشغيل بترتيب المفاتيح الأجنبية. ثم يتحقق المسؤول من وجود الجدول أو الفهرس المتوقع عبر `information_schema`. لا تجرى عمليات `DROP` أو تعديل مدمر في قاعدة الإنتاج دون خطة استرجاع مكتوبة ومراجعة أثر البيانات.

تصل الترحيلات الحالية إلى `0026_deep_bishop.sql`. تضيف الدفعات `0019`–`0025` نتائج صفوف الاستيراد وسياسات التكرار، وسجل التقارير الميدانية، وفحوصات الجودة، وأوامر الشراء وروابط العقود والالتزامات والاستلام، ثم سجل روابط الحوكمة وتوسعة أهدافه إلى RFI وNCR. تضيف `0026` جدول `master_plan_snapshots` ومفتاح إصدار باسم مختصر `mps_plan_version_fk` لتوافق حد معرّفات TiDB/MySQL. تحفظ نقطة تحقق بعد نجاح التحقق. النشر التلقائي المفعّل ينشر كل نقطة تحقق ناجحة على المجال الإنتاجي المتصل بالمشروع.

## قاعدة التكامل المعزولة

قاعدة الاختبار الحصرية هي `project_os_integration_test`. يشتق الإعداد عنوانها من `DATABASE_URL` ويطبق فقط الترحيلات غير المسجلة في جدول `integration_schema_migrations`.

```bash
cd /home/ubuntu/project-os
node scripts/setup-integration-test-db.mjs
node scripts/run-integration-database-test.mjs
```

يثبت المشغل اسم قاعدة البيانات قبل زرع أي بيانات مؤقتة. يجب أن يبقى اسمها `project_os_integration_test`؛ يعد ظهور اسم آخر فشلًا في العزل. تنظف الاختبارات المستخدمين والعضويات والأدوار والاستحقاقات والسجلات التشغيلية بترتيب يحترم المفاتيح الأجنبية.

## بوابة الإصدار

| البوابة | الأمر أو الدليل | معيار القبول |
|---|---|---|
| اختبارات الوحدة والواجهة | `pnpm test` | كل الاختبارات غير المشروطة ناجحة. |
| فحص الأنواع | `pnpm check` | ينتهي دون خطأ TypeScript. |
| بناء الإنتاج | `pnpm build` | ينتج حزمة العميل والخادم دون خطأ. |
| التكامل الحقيقي | `node scripts/run-integration-database-test.mjs` | يمر عند توفر قاعدة الاختبار؛ لا يُستبدل بمحاكاة. |
| العزل | حالات رفض مستأجر أو مشروع عابر في الاختبارات. | لا تنشأ سجلات ولا تُعاد بيانات عابرة. |
| التعريب | اختبار واجهة أو دليل DOM. | تظهر العربية والإنجليزية دون رسائل خادم خام. |

في آخر تحقق موثق اجتاز `pnpm coverage:trpc` مع **صفر إجراءات غير مصنفة**، و`pnpm test` **238 اختبارًا**، ونجح `pnpm check` و`pnpm build`، كما اجتاز مشغل MySQL/TiDB المعزول **55 حالة تكامل tRPC فعلية**. يغطي الجرد كل إجراءات الأعمال بمرجع مباشر، ويستثني فقط إجراءات الإطار الخمسة المسماة في `TEST_EVIDENCE_MATRIX.md`.

## المراقبة والاستجابة

تراجع سجلات التطوير محليًا من `.manus-logs/` عند ظهور خطأ خادم أو متصفح أو شبكة. في الإنتاج تراجع السجلات المنشورة عبر قناة سجلات الإنتاج. لا يفسر ظهور تحذير حجم حزمة Vite على أنه فشل نشر، لكنه يسجل كفرصة لتحسين التقسيم الديناميكي عند وجود عمل واجهة لاحق.

عند إخفاق الإصدار، يعاد تشغيل مسار التحقق لتحديد قابلية إعادة الإنتاج قبل نسبة الخطأ إلى تغيير بعينه. إذا تعذر الإصلاح المباشر، يستخدم الاسترجاع إلى آخر نقطة تحقق مستقرة؛ لا يستخدم `git reset --hard` في هذا المشروع.

## حدود موثقة

لا يدعم TiDB Serverless مشغلات قاعدة البيانات، لذلك لا يمكن في البيئة الحالية فرض منع `UPDATE` أو`DELETE` على `audit_logs` عبر trigger. تظل كتابة سجل التدقيق خادمية وذرية مع سجلات الأعمال، بينما تتطلب الحماية غير القابلة للتعديل على مستوى قاعدة البيانات بيئة MySQL/InnoDB أو حساب تشغيل منفصلًا وقيودًا بديلة.
