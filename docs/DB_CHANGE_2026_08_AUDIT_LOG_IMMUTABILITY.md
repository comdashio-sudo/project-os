# خطة تغيير قاعدة البيانات — عدم قابلية تعديل سجل التدقيق

## التغيير المخطط

إضافة مشغّلين على جدول `audit_logs` يرفضان أي `UPDATE` أو `DELETE` برسالة قاعدة بيانات صريحة. تبقى عمليات `INSERT` الموثقة من الخادم ممكنة، ولا يُضاف مسار تعديل أو حذف في طبقة التطبيق.

## الأثر المتوقع

| البند | الأثر المتوقع |
|---|---|
| السجل التاريخي | يصبح غير قابل للتعديل أو الحذف عبر أي عميل قاعدة بيانات اعتيادي. |
| الكتابات التشغيلية | تستمر عمليات الإدراج الذرية لسجل التدقيق بلا تغيير. |
| التكامل القائم | لا يتغير مخطط الأعمدة أو العقود البرمجية. |
| الأداء | تكلفة ضئيلة ومحصورة في محاولات التعديل أو الحذف المحظورة. |

## التنفيذ

ينفذ التغيير بترحيل SQL عبر إدارة قاعدة البيانات، مع إسقاط المشغلين بأمان قبل إعادة إنشائهما لضمان قابلية الإعادة. يستخدم كل مشغل `SIGNAL SQLSTATE '45000'` لمنع العملية.

## التحقق

يستخدم الاستعلام التالي للتأكد من وجود المشغلين:

```sql
SELECT TRIGGER_NAME, EVENT_MANIPULATION, ACTION_TIMING
FROM information_schema.TRIGGERS
WHERE TRIGGER_SCHEMA = DATABASE()
  AND EVENT_OBJECT_TABLE = 'audit_logs'
ORDER BY TRIGGER_NAME;
```

ويتحقق اختبار تكامل من رفض التعديل والحذف، مع بقاء الإدراج ممكنًا.

## الاسترجاع

إذا تطلبت حالة تشغيلية استثنائية إزالة الحماية، ينفذ مسؤول قاعدة بيانات مخول فقط:

```sql
DROP TRIGGER IF EXISTS audit_logs_block_update;
DROP TRIGGER IF EXISTS audit_logs_block_delete;
```

لا يغيّر الاسترجاع أي صف تاريخي، ويستلزم تسجيل سبب وقرار تغييري مستقل قبل تنفيذه.

## نتيجة التنفيذ في البيئة الحالية

لم يمكن تطبيق المشغّلين. أعادت قاعدة البيانات الفعلية الخطأ التالي عند أول عبارة DDL: `ERROR 1064 ... near "TRIGGER IF EXISTS ..."`. وتبين أن المحرك هو `8.0.11-TiDB-v8.5.3-serverless`، وتوضح وثائق TiDB الرسمية أن **Triggers** غير مدعومة.[1]

لذلك لا يجوز اعتماد شرط عدم القابلية للتعديل على مستوى قاعدة البيانات في هذه البيئة على أنه مغلق. الحماية التطبيقية الحالية هي كتابة سجلات التدقيق من الخادم فقط داخل معاملات ذرية، ولا توجد مسارات API لتعديلها أو حذفها؛ لكنها لا تعوض فرض قاعدة البيانات على عميل ذي صلاحيات مباشرة.

يتطلب الإغلاق الإنتاجي لهذه الفجوة أحد بديلين: قاعدة MySQL/InnoDB تدعم المشغلات، أو حساب تشغيل مستقل محدود الصلاحيات يملك `SELECT` و`INSERT` فقط على `audit_logs` ولا يملك `UPDATE` أو `DELETE`. لا يمكن إعداد البديل الثاني من المشروع لأن جلسة البيئة الحالية تستخدم حسابًا إداريًا مشتركًا واسع الصلاحيات.

[1]: https://docs.pingcap.com/tidb/stable/mysql-compatibility/ "TiDB: MySQL Compatibility — Unsupported features"
