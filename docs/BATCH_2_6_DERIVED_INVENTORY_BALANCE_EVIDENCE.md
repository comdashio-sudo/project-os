# دليل الدفعة 2.6 — رصيد المخزون المشتق

**الحالة:** `PROVEN` محليًا قبل الالتزام. أصبح رصيد مادة في مستودع نتيجة مجموع حركات `warehouse_inventory_transactions` ضمن المستأجر والمشروع والمستودع والمادة، وليس حقلًا تشغيليًا قابلًا للتحرير أو مصدرًا ثانيًا للقراءة.

| المتطلب | التنفيذ المثبت |
|---|---|
| مصدر الرصيد | خدمة `warehouses.list` تقرأ جميع حركات المشروع وتحسب `quantityOnHand` لكل زوج مستودع/مادة. الواجهة تعرض الناتج فقط ولا تعرض إدخالًا أو تعديلًا مباشرًا للرصيد. |
| الحارس الذري | قبل كتابة حركة جديدة، تقفل المعاملة صف المستودع نفسه بواسطة `SELECT … FOR UPDATE`، ثم تجمع الحركات للمادة بعد القفل وتحسب الرصيد التالي. إذا كان التالي سالبًا ترمي `PROJECT_OS_INVENTORY_INSUFFICIENT_STOCK` قبل أي إدراج حركة أو سجل تدقيق؛ وإذا كان غير سالب تكتب الحركة والتدقيق في المعاملة نفسها. |
| العزل والحراسة | تبقى العضوية والاستحقاق `PROJECT` وصلاحية `project.write` ونطاق المشروع والتحقق من المستودع والمادة قبل المعاملة. لا يمكن لمعّرف مستودع أو مشروع عابر الوصول إلى مسار الرصيد أو الكتابة. |
| الجدول القديم | فحص قرائي سابق أثبت أن `warehouse_stock_balances` يحوي صفر صفوف وصفر عدم تطابق. أعيدت تسميته عكسيًا على MySQL/TiDB إلى `_deprecated_warehouse_stock_balances` بترحيل `0044_rare_shinobi_shaw.sql`؛ أزيل من مخطط Drizzle النشط ولا تقرؤه الخدمة أو تكتبه. |

## الدليل الحي

| الحالة | الإثبات |
|---|---|
| ضمن الرصيد | استلام `10` ثم صرف `4` يعيدان على الترتيب `previousQuantity=0, nextQuantity=10` و`previousQuantity=10, nextQuantity=6`، وينشئان حركتين وسجلي تدقيق. |
| فوق الرصيد | محاولة صرف `7` من رصيد `6` تعيد `PROJECT_OS_INVENTORY_INSUFFICIENT_STOCK`. بعد الرفض يثبت الاستعلام مجموع الحركات `6.000` فقط، وعدد الحركات `2` وعدد سجلات التدقيق `2`؛ فلا توجد حركة أو تدقيق زائدان. |
| مصدر واحد | يثبت الاستعلام أن عدد الصفوف في جدول الرصيد القديم لنفس زوج المستودع/المادة هو `0` قبل إعادة التسمية، بينما تتطابق قراءة API مع مجموع الحركات. |
| العزل | يثبت السيناريو نفسه رفض إنشاء مستودع في مشروع عابر قبل أي حركة، مع بقاء الحارسات السابقة للمستأجر والمشروع والاستحقاق في المسار. |

## بوابة الجودة

| الأمر | النتيجة |
|---|---|
| `pnpm check` | ناجح بعد تحويل القراءة والكتابة والحارس الذري. |
| `node scripts/run-integration-database-test.mjs` | **75/75** ناجحة على MySQL/TiDB؛ يتضمن دليل عدم السالب بلا أثر ودليل السماح المدقق. |
| `pnpm drizzle-kit generate` | لا تغيير مخطط إضافي بعد 0044 وإزالة الجدول من نموذج Drizzle. |
| `git diff --check` | فروقات نظيفة قبل التوثيق النهائي. |

> **القيد المعلوم:** قراءة الرصيد تجمع الحركات كاملة الآن؛ لذلك تنمو كلفتها مع عدد الحركات. الحل المرشح لاحقًا هو **لقطة رصيد دورية محكومة** مع جمع الحركات اللاحقة فقط، لكنه ليس جزءًا من 2.6 ولا يجوز أن يصبح مصدرًا ثانيًا قابلًا للتحرير.
