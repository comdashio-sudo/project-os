# تدقيق الامتثال للمرجع الهندسي — PROJECT OS

**تاريخ التدقيق:** 19 أغسطس 2026.  
**النطاق:** النواة متعددة المستأجرين، RBAC، البيانات الرئيسية، Level 1–3، EVM، صحة المشروع، المستندات، RFI، NCR، العقود والالتزامات، ومحرك الاستيراد والتصدير.

> هذا التدقيق يصف ما ثبته الدليل المتاح في المستودع ونتائج التحقق، ولا يحوّل القيود أو الأعمال غير المختبرة إلى ادعاءات جاهزية.

## الدليل المنفذ

شُغلت بوابة التحقق التالية بعد دفعة نتائج صفوف الاستيراد وأنماط التكرار:

```text
pnpm test && pnpm check && pnpm build
```

وكانت النتيجة: **210 اختبارات وحدة وواجهة ناجحة**، ثم نجاح فحص TypeScript وبناء الإنتاج. كما اجتاز مشغل MySQL/TiDB المعزول **34 اختبار تكامل فعليًا**، بينها رفض قراءة تفاصيل استيراد من مشروع عابر، والسماح بسياسات `upsert` و`skip_duplicates` و`update_existing` مع نتائج صفوف وعدادات وتدقيق. كما فُحصت الواجهة بحثًا عن `error.message` أو بدائلها الشائعة، ولم يظهر استخدام مباشر في ملفات `.tsx`. وفُحصت طبقة الخادم بحثًا عن `update(auditLogs)` أو `delete(auditLogs)`، ولم يظهر أمر من هذا النوع.

## مصفوفة الامتثال

| قاعدة المرجع | حالة الفرض | الدليل الحالي | الحد أو الفجوة المتبقية |
|---|---|---|---|
| الدليل لا الادعاء | مطبق في الدفعات المكتملة | كل نقطة تحقق حديثة تسجل عدد الاختبارات، وTypeScript، والبناء. | لا يكفي البناء وحده؛ التحقق البصري بحساب مصرح به ما زال مطلوبًا لبعض المسارات. |
| الحالة الخاطئة مستحيلة | جزئيًا، بالخادم وقاعدة البيانات | المفاتيح الأجنبية، مفاتيح المستأجر، خرائط انتقالات RFI/NCR/المستندات/دورة حياة المشروع، وحراس التفويض قبل الكتابة. | TiDB Serverless لا يدعم المشغلات المطلوبة لقفل `audit_logs` على مستوى قاعدة البيانات. |
| عزل المستأجرين والمشروع | مطبق في المسارات المغطاة | `tenantId` على السجلات التشغيلية، حارس ملكية المشروع، واختبارات رفض العبور للعقود والمستندات وRFI وNCR وبيانات PMO ومصدر صحة المشروع، إضافة إلى تكامل MySQL/TiDB يرفض WBS من مشروع شقيق قبل كتابة الميزانية والتكلفة والتقدم. | تستمر الحاجة إلى دليل رفض وسماح فعلي لكل مسار تشغيلي جديد أو معرّف نطاق جديد. |
| صلاحيات الكتالوج | مطبق في RBAC والمسارات المغطاة | صلاحيات `tenant.manage` و`executive.read` و`pmo.read` و`pmo.write` و`project.read` و`project.write` عبر `assertTenantAccess`. | يلزم استمرار إضافة دليل رفض وسماح صريحين لكل مسار جديد. |
| لا أحد يعدّل سلطته | مطبق للمسارات المعروفة | اختبارات ترفض تعديل دور المنفذ، تعيينه، أو إلغاء إسناده. | يجب مراجعة كل مسار كتابة جديد عند إضافته، خصوصًا أي إدارة مستقبلية للعضويات. |
| تاريخ غير قابل للتزوير | مطبق خادميًا مع قيد بيئي | كتابات التدقيق تنشأ من الخادم ضمن معاملات مع الكتابات التجارية؛ لا يقبل العميل هوية منفذ سجل التدقيق. | منع التحديث والحذف لا يمكن فرضه حاليًا بالمشغلات في TiDB؛ الفجوة موثقة ولا تُدّعى مغلقة. |
| الدفعات المنضبطة | مطبق في الترحيلات المنفذة حتى 0019 | وثقت خطة `MIGRATION_PLAN_0019_IMPORT_ROW_RESULTS.md` الأثر والتحقق والاسترجاع، ثم أضيف جدول نتائج الصفوف دون تعديل هَدمي. | يجب الاستمرار بكتابة خطة وأثر واستعلام تحقق ومسار استرجاع قبل أي ترحيل جديد. |
| المسارات الشقيقة | مطبق في آخر الدفعات | مصدر الصحة يختبر RFI وNCR، والكتابات تختبر الإنشاء والانتقال والقراءة حيث ينطبق. | يلزم فحص الإنشاء والتحديث والانتقال والقراءة المتجاورة عند كل إصلاح جديد. |
| العربية والإنجليزية وRTL/LTR | مطبق للواجهات المختبرة | `LanguageContext` وزر اللغة، واختبارات واجهات للسجلات ورسائل الأخطاء، وفحص عدم عرض `error.message` في `.tsx`. | يلزم اختبار كل واجهة جديدة بالعربية والإنجليزية، مع تحقق بصري لحساب مصرح به حين تتوفر بياناته. |
| النسبة لا العدد المضلل | مطبق في المؤشرات الحالية | تعرض بطاقة الصحة عدادات مصادر صريحة، ومنها `overdueRfiCount` و`overdueNcrCount`. | لا تعرض نسب صحة إضافية إلا إذا عُرّف مقامها ومصدرها صراحة. |

## تدقيق معالج الاستيراد ونتائج الصفوف

| بند | النتيجة المثبتة |
|---|---|
| نقطة التقارب | يفرض التحليل والتأكيد وقراءة التفاصيل عضوية المستأجر وحزمة PROJECT وصلاحية المشروع وميزة `DATA_IMPORT` وملكية المشروع قبل التخزين أو القراءة أو الكتابة. |
| سياسة التكرار | ترفض المفاتيح المكررة داخل الملف دائمًا. تطبق السجلات الموجودة مسبقًا سياسة محفوظة: إيقاف، تجاوز، تحديث موجود فقط، أو upsert. |
| أثر الصف | تسجل المعاملة نتيجة كل صف صحيح في `data_import_row_results` مع رقم الصف والمفتاح والإجراء ومعرف السجل عند وجوده، وتحدث عدادات الإنشاء والتحديث والتجاوز في سجل الاستيراد نفسه. |
| الرفض والعزل | يثبت تكامل MySQL/TiDB رفض قراءة تفاصيل سجل استيراد من مشروع مستأجر آخر قبل إعادة النتائج. |
| السماح | يثبت التكامل `upsert` لتحديث سجل WBS وإنشاء آخر، ثم يثبت `skip_duplicates` و`update_existing` بعدادات وسجلات صفوف متوقعة. |
| الواجهة والتعريب | تثبت اختبارات DOM اختيار سياسة التكرار، وعرض نتائج الصفوف، وتوطين السياسة والإجراءات بالعربية والإنجليزية، من دون رسالة خادم خام. |

## تدقيق خاص بمصدر NCR لصحة المشروع

| بند | النتيجة المثبتة |
|---|---|
| نطاق الاستعلام | يحصر الاستعلام `ncrs` بالمستأجر والمشروع، ويقتصر على السجلات ذات الاستحقاق الماضي والحالات غير المغلقة وغير الملغاة. |
| أثر الصحة | يمرر `overdueNcrCount` إلى مصدر اللقطة والحساب والسجل التدقيقي. |
| العرض | يحلل العميل القيمة عددياً فقط، ويتجاهل القيم غير الصالحة، ثم يعرض العداد بنص عربي أو إنجليزي. |
| عزل المصدر | اختبار صريح يثبت أن NCR متأخرًا خارج المشروع لا يدخل العداد؛ العدد الناتج صفر ودرجة اللقطة تبقى وفق المصادر الموجودة فقط. |
| التحقق | نجح الاختبار المتخصص، ثم اجتاز التحقق الشامل 150 اختبارًا وفحص TypeScript والبناء. |

## تدقيق نطاق WBS للمسارات المالية والتقدم

| بند | النتيجة المثبتة |
|---|---|
| نقطة التقارب | تستدعي `createBudgetLine` و`createCostEntry` و`createProgressEntry` الحارس `assertWbsItemWithinProject` قبل بدء المعاملة عند ورود معرف WBS. |
| رفض المشروع الشقيق | أنشأ التكامل مشروعًا شقيقًا في المستأجر نفسه وWBS تابعًا له، ثم رُفضت محاولات ميزانية وتكلفة وتقدم في المشروع الأصلي بالرمز `PROJECT_OS_WBS_SCOPE_MISMATCH`. |
| السماح الصحيح | أنشأ التكامل WBS مملوكًا للمشروع الأصلي ثم كتب الميزانية والتكلفة والتقدم بنجاح. أعاد استعلام التحقق ثلاثة صفوف مصرح بها وصفر كتابة للـWBS الشقيق. |
| التحقق | اجتاز مشغل MySQL/TiDB 32 حالة فعلية؛ تليه بوابة `pnpm test && pnpm check && pnpm build`. |

## الأعمال المفتوحة التي لا يدعي هذا التدقيق إغلاقها

1. اختيار بيئة MySQL/InnoDB أو ضابط تشغيل مكافئ لفرض منع تحديث وحذف `audit_logs` خارج TiDB Serverless.
2. تنفيذ الإشعارات المعتمدة على الاستثناءات والموافقات، مع دليل تسليم وفشل موطّن.
3. استكمال الوحدات التشغيلية المفتوحة وتوسيع أدلة العزل والتعريب معها.

## قرار قاعدة البيانات التشغيلي

المصدر المعتمد للمشروع الحالي هو **MySQL/TiDB Serverless**. يثبت ذلك استخدام `drizzle-orm/mysql2` و`mysqlTable` وملفات الترحيل بصيغة MySQL، إضافة إلى الاتصال الحي بقاعدة مشروع PROJECT OS. لا يعد Supabase/PostgreSQL جزءًا من هذه المعمارية؛ وأي تحويل إليه تغيير معماري مستقل لا يصح دمجه ضمن اختبار تكامل أو تغيير تشغيلي صغير.

## قاعدة الاستمرار

لا تغلق أي دفعة لاحقة إلا بعد كتابة دليل تحقق قابل لإعادة التشغيل، وتسجيل ما لم يتحقق وسببه، وتحديث هذه المصفوفة أو حالة المشروع عند تغير قيد أو فجوة.
